## 2. 收反馈

设置页「消息」组有一行「反馈与建议」。页内注释写明：「我的反馈」和「提供建议」并成这一行，进去先看往来，底部写建议。同文件还留着标题为「提供建议」的弹窗，弹窗说明是「被采纳的建议会写进更新公告」。

`submitFeedback` 收下的内容：

- 玩家填的：标题、正文（至少 5 个字）、类型、选填联系方式、图片。
- 程序附上的：用户标识、昵称、设备信息（品牌、机型、系统、微信版本等）、小程序版本、来源页。来源页默认 `about`。
- 限流：1 分钟一条，24 小时最多 10 条。2026-10-07 的 PRD 把每日上限从 5 改成 10，代码里的常量是 10。

写入两处：微信云数据库 `feedback`，以及飞书多维表格「DND 小程序用户反馈」的「反馈记录」。飞书同步失败只记在本地记录上，玩家那边仍然提交成功。表字段以 `docs/routines/feedback.md` 为准：反馈标题、反馈内容、类型、状态、优先级、来源页面、提交时间、用户标识、设备信息、小程序版本、AI 摘要、Issue 链接、处理备注、微信记录ID、加急金额。联系方式和用户标识留在飞书表，不进 Linear。

`docs/PRD-反馈飞书同步.md` 文末仍写着「配置云函数环境变量：未完成」「截图验收：未完成」。那份 PRD 的任务表没有随代码改口。代码里同步函数已经在，环境变量没配齐时会跳过飞书。这次没有查云端环境变量，不把「每一条都已经进飞书」写成已核实。

## 4. 分诊，以及回到用户

issue 管家每轮补项目、端标签、优先级和阻塞关系；大需求新建功能项目，按前端 / 后端 / 美术切开，用 blocked by 串起来。规则在 `docs/routines/triage.md`，2026-11-15 车主定（HAN-1769）。评论标记仍是 `【分诊】`。

回到玩家这边，三件事要分开：

**回复和金币，代码在，现行提示词没接上。** `getMyFeedback` 会把 `reply`、`rewardGold` 返回给「反馈与建议」。`submitFeedback` 里有一段定时入口：飞书行填了「奖励档位」、且「回写状态」为空时，把回复写回小程序，并按档位建奖励单。档位金额写在云函数里（2026-10-29 车主把单条上限调到 10 金币，见该 PRD）。现行 `docs/routines/feedback.md` 的开单步骤不填「奖励档位」和「给玩家的回复」。云端定时器有没有打开，这次没进微信云控制台。页面不讲「有效反馈自动发金币」。

**公告和版本更新，玩家现在看得到。** 设置页「公告」和「版本更新」各一行。公告走云函数 `manageNotices`，管理员可以新建、编辑。版本更新是更新日志列表。执行任务的约定是：玩家能感知的改动，在 PR 里加 `changes/unreleased/` 碎片（`docs/routines/claude-exec.md`）。2026-10-07 的 PRD 写明不做一件事：修复上线后，不自动把这条反馈改成「已解决」。

**加急没上。** 项目「反馈加急通道」状态 Planned（2026-11-15 建）。HAN-1746（后端）和 HAN-1747（公众平台登记道具）都还在 Backlog。`miniprogram/config/features.js` 里没有加急开关。页上不出现加急。

## 7. 不是从玩家反馈来的

**工作流告警会开单，抽到的那张没有改代码。** `.github/workflows/workflow-alert.yml`：被盯的工作流失败时，往固定的「工作流故障日志」追加评论。HAN-1625 正文写明，本单由 `workflow-alert` 自动创建，同一步骤 7 天内只开一条。它在 2026-11-08 18:18 开出，18:38 关掉。关掉时的评论说：微信上传接口返回空内容，同一设置重跑已经成功，不是代码缺陷，所以不改基建。这条评论没有 `【AI回复】` 署名。

**cloud-diag 是人手触发的只读检查。** `.github/workflows/cloud-diag.yml` 只在 `workflow_dispatch` 时跑，自检或看云函数日志，不改配置、不部署。它在 workflow-alert 的监听名单里，失败会留痕。没有看到它自己开出修复单并合入代码。HAN-1681 的 Codex 评论写过一次只读调用，日志 0 条。

**gate-watchdog 也是人手触发。** 它扫开着的、基线为 `dev` 的 PR，头提交上没有检查就在 PR 下提醒。自己不改产品代码。

**经营分析没有这条闭环。** 搜到的是带「经营分析」标签的分析单，例如 HAN-685「经营分析总览：We分析数据体检（2026-09）」，2026-09-27 开，2026-10-31 完成。它不是「巡航发现一个故障 → 自动开单 → 代码合入」。

页上不放这一节。讲者备注用 HAN-1625 那一句即可：机器会把失败写成单，这张单最后是重跑成功关掉的。

## 8. 市面上的一手说明

只收官方文档或官方博客。页面无日期的，记下查阅日 2026-11-18。

**Sentry Seer Autofix，对应「报错之后可以修到 PR」。** [官方文档](https://docs.sentry.io/product/ai-in-sentry/seer/autofix/)（2026-11-18 查阅；页首写明 2026-12-08 起改按用量计费）。它用报错、追踪、日志和仓库找根因，可以停在根因、停在方案，或开出 PR。自动跑要同时满足：至少 10 次事件、14 天内发生、模型觉得修得动。开了 PR 之后，人再合；文档写 “Review the resulting changes before merging the PR.” 和我的流程比：它从监控进，不从玩家的一句话进；它能自己开 PR，我这边的 workflow-alert 停在开单。

**Linear Triage Intelligence，对应分诊，不停在写代码。** [官方文档](https://linear.app/docs/triage-intelligence)（2026-11-18 查阅，页上无日期）。Business 和 Enterprise 才有。新进分诊的单会被模型看过，建议团队、项目、负责人、标签，也可以建议和旧单的关系；建议可以设成自动套用。和我的 issue 管家比：它补的是字段，不建项目、不切片、不开 PR。

**GitHub Copilot，对应「把单派给写代码的 AI」。** 官方博客 [GitHub Copilot: Meet the new coding agent](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/)（2025-05-19，2025-05-23 更新）写：把 GitHub issue 派给 Copilot，它在 Actions 里开一台机器，把进度推成草稿 PR。现行文档已改称 Copilot cloud agent。[Assign an issue to Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task)（2026-11-18 查阅）写：“Assigning an issue always creates a pull request.” 同一组文档还写可以从失败的 GitHub Actions 启动。和我的流程比：派单之后它负责写到 PR；合入仍要人看。我这边开单和写代码是两个定时任务，中间还过一次分诊。

**OpenAI Codex 接在 Linear 上，形状和 Copilot 派单接近。** [Use Codex in Linear](https://learn.chatgpt.com/docs/third-party/linear)（2026-11-18 查阅，页上无日期）。把单派给 Codex，或在评论里写 `@Codex`，它开一轮云端对话，做完后把摘要和对话链接写回这张单，人再从对话开 PR。分诊规则可以设成「进入分诊就派给 Codex」。和 Copilot 放在一起会重复，页上用 Copilot，这则留在讲者备注。

Devin 这次没有找到一份官方原文，能按「收到反馈 / 报错 → 开单 → 改代码 → 人合入」对齐到我的某一环，所以不写。
